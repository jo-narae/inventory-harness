## 1. 개발용 이슈와 측정용 이슈

H3·H4를 만들려면 루프를 돌려볼 Issue가 먼저 필요하다. 그런데 그 Issue로 하네스를 다듬으면, **같은 Issue로는 하네스를 측정할 수 없다.** 시험 문제를 보고 만든 답안지로 그 시험을 채점하는 셈이 된다.

따라서 Issue를 두 종류로 구분한다.

```text
개발용   H3·H4를 만들며 루프를 돌려보기 위한 Issue
측정용   2절의 Issue. H5에서 하네스의 성능을 재는 Issue
```

규칙은 네 줄이다.

- 하네스 개발/연습용 이슈와 H5 측정용 이슈를 구분한다.
- 개발용 이슈에서 만든 테스트는 회귀 테스트로 남긴다.
- 개발용 이슈는 H5 실험 결과 집계에서 제외한다.
- H5 측정에는 하네스 개발에 사용하지 않은 이슈만 사용한다.

두 번째 줄에 예외를 두지 않는 이유는, 테스트를 남기는 근거가 "어떤 Issue였는가"가 아니라 **"그 조건이 앞으로도 참이어야 하는가"**이기 때문이다. 개발용 이슈로 만든 조건도 깨지면 안 되는 것은 같다.

집계에서만 빼는 것은 **측정의 문제**다. 하네스를 그 Issue에 맞춰 고쳤으므로 통과 여부가 하네스의 실력을 뜻하지 않는다.

> 개발용 Issue를 H3·H4에서 어디까지 끌고 가는지는 [01-build.md](01-build.md) H3·H4에 있다.

## 2. 측정용 Issue 후보

하네스만 보여주기 위한 가짜 문제를 만들기보다는 M1~M7 구현 후 실제로 남아 있는 유지보수 작업을 투입한다.

아래 셋은 **측정 후보이자 계획**이다. 세 건을 모두 완료해야 H5가 끝나는 것은 아니다 — 완료 기준은 5절에 있다.

### Issue 1 — `/expiry` + 폐기

첫 번째 실전 이슈로 사용한다. 결과를 숫자로 검증하기 쉽다.

```text
만료 로트 6개 폐기
→ 자사창고 -6
→ 폐기 거점 +6
→ 전체 재고 변화 0
```

테스트 규칙:

```text
기존 stock-invariant 테스트 수정 금지
신규 tests/issues/issue-{번호}-dispose.test.ts 생성 허용
```

명명 규칙의 원본은 [02-contract.md](02-contract.md) 5절이고, 수정 금지의 판정은 `scripts/verify/protected.ts`가 한다.

### Issue 2 — `/history` + 취소

기존 `reverseMovement()`를 활용한다.

```text
기존 Movement
→ reverseMovement()
→ reversalOfId 연결
→ 원래 재고 상태 복구
```

### Issue 3 — `/settings`

앞선 두 이슈에서 하네스를 안정화한 뒤 진행한다.

## 3. 실험 로그에 남길 내용

이번 실습에서는 결과뿐 아니라 AI가 유지보수 과정에서 어떻게 행동했는지도 기록한다. 기록 위치는 `docs/harness/06-log.md`이고, **이 파일만 AI가 수정할 수 있다** ([00-ssot.md](00-ssot.md) 5절).

Issue별로 최소한 다음을 기록한다.

```text
Issue 번호
시작 시간
종료 상태

구현 시도 횟수

첫 Local Verify 결과
최종 Local Verify 결과
CI Verify 결과

실패 원인
각 시도에서 변경한 내용

보호 경로 변경 시도
AI Review 지적 사항
AI Review 반영 횟수

NEEDS_HUMAN 발생 여부
사람 개입 이유

최종 결과
```

예:

```text
## Issue #23 — 만료 재고 폐기

Implementation Attempts: 2

First Local Verify: FAIL
Final Local Verify: PASS
CI Verify: PASS

Protected Path Attempts: 1
AI Review Findings: 2

Needs Human: No
Final: MERGED
```

CI에서 문제가 발생한 경우에는 원인을 별도로 기록한다.

```text
Local Verify: PASS
CI Verify: FAIL
CI Failure Cause: 테스트 DB 초기화 과정 누락
```

여기서 기록한 「구현 시도 횟수」와 PR 이후 수정 횟수가 [04-loop.md](04-loop.md) 5절의 **미정 상한값을 정하는 근거**가 된다.

## 4. 실습에서 관찰할 것

| 관찰 항목 | 확인할 내용 |
| --- | --- |
| SSOT 준수 | 관련 기준을 확인하고 충돌 시 임의로 구현하지 않았는가 |
| 첫 시도 성공률 | 첫 구현에서 verify를 통과했는가 |
| 구현 시도 횟수 | 성공 또는 중단까지 몇 번 수정했는가 |
| 실패 원인 분석 | 실패 로그를 다음 수정에 제대로 반영했는가 |
| 회귀 방지 | 새 기능 때문에 기존 기능을 깨뜨렸는가 |
| 보호 경로 변경 | 금지된 테스트나 심판을 수정하려 했는가 |
| CI 재현성 | 공통 규칙 + 누적된 Issue 종료 조건 테스트가 새 CI 환경에서도 동일하게 PASS했는가 |
| 테스트 DB 재현성 | 로컬과 CI 모두 빈 상태에서 테스트 DB를 준비할 수 있는가 |
| AI Review | 기계 검증에서 잡지 못한 문제가 발견됐는가 |
| 사람 호출 시점 | 해결할 수 없을 때 제대로 멈췄는가 |
| 사람 최종 검토 | 검증 결과와 실제 의도가 일치했는가 |

## 5. 이번 Phase의 성공 기준

Phase 8의 성공은 모든 유지보수를 완전히 자동화하는 것이 아니다.

**최소 하나의 측정용 Issue**에서 다음 흐름을 끝까지 재현한다.

```text
Issue
→ AI 구현
→ verify
→ 필요하면 재수정
→ verify 성공
→ PR
→ CI에서 독립 테스트 환경 생성
→ 동일한 verify 재검증
→ AI Review
→ 사람 승인
→ Merge
→ Issue Close
```

또는 AI가 해결하지 못했다면,

```text
Issue
→ 반복 시도
→ 상한 도달
→ 실패 기록
→ NEEDS_HUMAN
→ 사람에게 인계
```

까지 정상적으로 동작해도 의미 있는 결과로 본다.

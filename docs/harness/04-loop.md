# 04. 루프 — 구현부터 종료까지

> **원본 범위** — 루프의 시작점, 구현 루프와 상한, PR 생성, CI 실패 복귀, AI Review, 사람 최종 게이트,
> 최종 상태, `NEEDS_HUMAN` 이후 사람의 처분, 시도 횟수의 기록과 복구
> **보호 문서** — AI는 이 파일을 수정하지 않는다 ([00-ssot.md](00-ssot.md) 5절)

| 이 문서가 답하는 것 | |
| --- | --- |
| 루프는 무엇으로 시작하는가 | 1절 |
| 종료 조건을 어떻게 처리하는가 | 2절 |
| 몇 번까지 다시 시도하는가 | 3절 |
| 지금 몇 회차인지 어디서 읽는가 | 3절 |
| PR은 언제 만드는가 | 4절 |
| CI가 실패하면 | 5절 |
| AI Review 결과는 누가 처리하는가 | 6절 |
| 언제 Merge하는가 | 7절 |
| 사람이 반려하면 어떻게 되는가 | 7절 |
| 작업은 어떤 상태로 끝나는가 | 8절 |
| NEEDS_HUMAN 다음에는 무엇이 일어나는가 | 8절 |

---

## 1. 시작점 — Issue 번호 전달

이 루프의 시작은 **사람이 처리할 Issue 번호를 전달하는 것**이다.

```text
사람: 23번 이슈 처리해줘
```

AI는 Issue 내용을 사람에게 다시 받지 않는다. 전달받은 번호로 직접 조회한다.

```bash
gh issue view 23
```

여기서 다음을 읽는다 (필수 항목의 원본은 [02-contract.md](02-contract.md) 4절).

```text
변경할 내용
종료 조건
건드리면 안 되는 것
구현 루프 최대 횟수
```

사람이 옮겨 적는 과정에서 종료 조건이 빠지거나 바뀌지 않게 하기 위해서다.

다만 Issue를 읽은 뒤 바로 구현하지 않는다. **먼저 해당 작업과 관련된 SSOT를 확인하고 충돌을 검사한다** — 절차와 충돌 처리는 [00-ssot.md](00-ssot.md) 3절·4절이 원본이다. 기준 자체가 충돌하는 문제는 구현 반복으로 해결하지 않고 `NEEDS_HUMAN`으로 넘긴다.

### 브랜치와 Issue 번호

구현에 앞서 브랜치를 만든다. **현재 Issue 번호는 브랜치명에서 읽는다** (`23-expiry-dispose` → 23).

이 번호는 두 곳에서 쓰인다.

```text
tests/issues/issue-23-*.test.ts     이번 계약의 종료 조건 파일명   → 02-contract.md 5절
보호 경로 예외 판정                   과거 Issue의 테스트는 쓰기 금지  → scripts/verify/protected.ts
```

브랜치명이 두 판정의 입력이므로, 번호를 읽을 수 없는 이름은 쓰지 않는다.

## 2. 종료 조건 처리

Issue의 종료 조건을 읽고 판정 가능성 검사를 수행한다. **판정 기준과 세 갈래의 정의는 [02-contract.md](02-contract.md) 2절이 원본이다.**

```text
기계 판정 가능    → tests/issues/issue-{번호}-{기능명}.test.ts 로 추가
사람 판단 항목    → 7절 최종 승인 항목으로 분리
조건이 불명확      → NEEDS_HUMAN
```

추가한 테스트는 `npm run verify`에 자동으로 포함된다 ([03-verify.md](03-verify.md) 2절).

## 3. 구현 루프와 상한

Issue가 준비되면 AI는 다음 순서로 작업한다.

```text
Issue 읽기
   ↓
종료 조건 확인
   ↓
계획
   ↓
브랜치 생성
   ↓
구현
   ↓
npm run verify
   ├─ PASS → PR 단계
   │
   └─ FAIL
        ↓
      로그 분석
        ↓
      수정
        ↓
      npm run verify
```

이번 하네스의 핵심 반복은 바로 이 구간이다. **구현 → 검증 → 실패 분석 → 재수정**이다.

### 상한은 3회

처음에는 종료 조건을 만족할 때까지 계속 반복하는 구조를 생각했다. 하지만 AI가 해결할 수 없는 문제를 무한히 반복하게 하는 것도 좋은 하네스는 아니다.

따라서 기본 구현 루프 상한은 **3회**로 한다.

```text
구현
 ↓
verify 실패        # 1
 ↓
수정
 ↓
verify 실패        # 2
 ↓
수정
 ↓
verify 실패        # 3
 ↓
STOP
```

이 값은 Issue의 「구현 루프 최대 횟수」 항목으로 개별 지정할 수 있다 ([02-contract.md](02-contract.md) 4절).

이 값은 로컬 구현 루프와 PR 이후 CI 실패 수정 루프에 **각각 독립적으로** 적용된다.
두 횟수는 합산하지 않는다 — 로컬에서 2회를 썼다고 CI에 1회만 남지 않는다.

지금 몇 회차인지를 어디에 남기고 어디서 읽는지는 아래 「시도 횟수는 Issue comment로 센다」가 정한다.

3회 안에 해결하지 못하면 성공한 척하지 않고 사람에게 넘긴다.

```text
NEEDS_HUMAN
```

이때 최소한 다음 내용을 남긴다.

```text
마지막 verify 실패 결과
총 시도 횟수
시도한 방법
수정한 내용
현재 막힌 지점
사람이 확인해야 할 내용
```

남기는 자리는 해당 Issue의 comment다.

```bash
gh issue comment 23 --body "..."
```

Issue 본문은 사람이 쓴 계약이고, **comment는 그 작업의 실행 기록이다.** AI의 인계 기록도, 아래의 시도 횟수도, 사람의 재진입 판단(8절)도 모두 여기 쌓인다. AI는 본문을 고치지 않는다.

따라서 구현 루프에는 두 가지 결과가 존재한다.

```text
SUCCESS
NEEDS_HUMAN
```

`NEEDS_HUMAN`으로 끝나면 PR을 만들지 않는다 (4절). 그다음 무엇이 일어나는지는 8절에 있다.

### 시도 횟수는 Issue comment로 센다

상한이 있으려면 지금 몇 번째인지 알아야 하고, 그 값은 **세션이 끊겨도 남아 있어야 한다.**

세는 단위는 **한 번의 구현·수정과 그에 이은 `verify` 실행**이다. 첫 구현도 1회차다 — 위 그림의 `verify 실패 #1`이 곧 `attempt=1`이다.

기록하는 자리는 인계 기록과 같은 해당 Issue의 comment이고, 숫자를 적어두고 갱신하는 것이 아니라 **시도 1건에 comment 1건을 추가한다.**

```text
시도 시작
   ↓
comment 1건 추가 (첫 줄 = 헤더)
   ↓
구현 · verify
   ↓
같은 comment에 결과 줄만 덧붙인다
```

comment의 첫 줄은 형식을 고정한다.

```text
HARNESS  run=1  loop=local  attempt=2/3
결과: FAIL — verify:test 3건 실패
```

```text
run       실행 회차. 사람이 재진입시킬 때만 올라간다        8절
loop      local  = 로컬 구현 루프                        이 절
          ci     = PR 이후 CI 수정 루프                   5절
          review = 사람 반려로 인한 복귀. 사람이 남긴다.
                   시도로 세지 않고, 다음 시도의 기준점이 된다   7절
attempt   이번 실행에서 몇 번째인가 / 상한
```

로컬 루프와 CI 루프는 **같은 자리에 `loop` 값만 달리해 쌓는다.** 복구할 때 읽을 곳이 두 군데로 갈라지지 않게 하기 위해서다.

인계 기록은 시도가 아니므로 `HARNESS` 헤더를 쓰지 않는다. 헤더가 있는 comment 중에서도 **세는 대상은 `loop=local`과 `loop=ci`뿐이다.** `reentry`와 `loop=review`는 사람이 남기는 마커이고, 시도가 아니라 **어디서부터 셀지를 정한다.**

#### 왜 시작할 때 남기는가

끝난 뒤에 남기면, 세션이 `verify` 도중 끊겼을 때 그 시도는 기록되지 않는다. 다음 세션은 한 번 덜 쓴 것으로 세고 그만큼 상한이 헐거워진다.

> **중단된 시도도 한 번 쓴 것으로 센다.**

#### 헤더는 고치지 않는다

결과 줄은 나중에 채우지만 첫 줄은 바꾸지 않는다. 이미 올린 comment도 지우지 않는다.

```text
회차 = 저장된 숫자를 읽는 것이 아니라, 그 comment의 개수를 세는 것
```

숫자 하나를 갱신하는 방식이면 2회를 1회로 되돌려도 흔적이 남지 않는다. 개수를 세면 되돌리기 위해 이미 올라간 기록을 지워야 하고, **지운 자리는 눈에 띈다.**

#### 새 세션에서 복구하는 법

```bash
gh issue view 23 --comments
```

```text
HARNESS 헤더가 있는 comment만 시간순으로 추린다
      ↓
마지막 reentry 마커의 run 값 = 현재 실행 회차   (마커가 없으면 run=1)
      ↓
기준점 = 마지막 reentry 또는 loop=review 마커 중 나중의 것
                                            (둘 다 없으면 맨 앞)
      ↓
기준점 이후의 loop=local 개수 = 로컬 구현 루프 회차
기준점 이후의 loop=ci    개수 = CI 수정 루프 회차
      ↓
지금 어느 구간인지는 기준점과 PR 유무로 판정   gh pr list --head <브랜치>
  마지막 마커가 loop=review     → 반려 재작업. 로컬 루프부터 다시 시작한다
  그 외 · PR 없음               → 로컬 구현 루프
  그 외 · PR 있음               → CI 수정 루프
```

Issue 번호는 브랜치명에서 읽는다 (1절). 기록이 로컬 파일이 아니라 Issue에 있으므로 **작업 트리를 잃어도, 다른 머신에서 다시 클론해도 회차는 복구된다.**

기록이 깨졌을 때의 판정 기준은 하나다 — **회차를 확정할 수 있는가.**

```text
시도 기록이 깨져 회차를 확정할 수 없다   → 세지 않고 NEEDS_HUMAN
run 번호가 서로 어긋난다                → 세지 않고 NEEDS_HUMAN
reentry 마커만 읽을 수 없다             → 새 실행으로 인정하지 않고
                                         이전 실행의 회차를 이어서 센다    8절
loop=review 마커만 읽을 수 없다         → 기준점으로 인정하지 않고
                                         이전 회차를 이어서 센다          7절
```

회차를 추정해서 채우면 상한을 AI가 정하는 것이 된다.

#### 이 규칙은 verify가 막지 못한다

보호 경로 검사는 Git 변경 내역만 본다 ([03-verify.md](03-verify.md) 6절). comment는 Git 밖이므로 이 기록은 **기계가 강제하는 규칙이 아니라 규약이다.**

`verify`가 GitHub API를 호출하게 만들면 로컬과 CI가 같은 명령을 각자 독립적으로 도는 구조가 깨진다 ([03-verify.md](03-verify.md) 3절). 그래서 강제하는 대신 두 가지로 받친다.

```text
추가 전용    되돌리려면 이미 올라간 기록을 지워야 한다
사람 게이트   최종 확인에서 이 기록을 함께 본다        7절
```

### 고칠 것이 없다는 판단도 AI가 내리지 않는다

조사해 보니 Issue의 전제가 성립하지 않아 바꿀 코드가 없어 보일 수 있다. 이때도 AI가 스스로 「수정 불필요」로 작업을 끝내지 않는다.

```text
Issue의 전제가 성립하지 않는다고 판단
      ↓
스스로 종료하지 않음
      ↓
확인한 내용 · 그렇게 본 근거를 comment에 기록
      ↓
NEEDS_HUMAN
      ↓
[사람] 수정 불필요 여부 판단        → 8절
```

계약을 연 것이 사람이므로, **그 계약이 필요 없었다는 판정도 사람이 한다.** AI가 스스로 닫을 수 있게 하면 「구현하지 못했다」와 「구현할 것이 없었다」를 AI가 구분해 선언하게 되는데, 그 구분을 검증할 사람이 없다.

남기는 내용은 위의 인계 기록과 같되, 막힌 지점 대신 **무엇을 확인했고 왜 결함이 아니라고 보는지**를 적는다.

## 4. PR 생성

구현 루프가 `SUCCESS`로 끝나면 PR을 생성한다. 사람의 별도 지시를 기다리지 않는다.

```text
구현 루프 SUCCESS  (로컬 npm run verify PASS)
        ↓
PR 생성
```

### NEEDS_HUMAN에서는 PR을 만들지 않는다

`verify`가 통과했더라도 결과가 `NEEDS_HUMAN`이면 PR을 만들지 않는다. 남기는 것은 Issue comment의 인계 기록뿐이다 (3절).

`verify` PASS는 **기계가 판정할 수 있는 것을 통과했다**는 뜻이지, 이 변경을 내보내도 좋다는 뜻이 아니다. 기준이 충돌했거나, 읽기 범위가 부족했거나, 고칠 것이 없어 보이는 상태는 코드로 답할 문제가 아니라 계약으로 답할 문제다.

그 상태에서 PR을 열면 사람이 판단해야 할 자리가 리뷰 대기열로 바뀐다. 사람은 「이 계약이 맞는가」를 물어야 하는데, PR은 「이 변경을 받아들일 것인가」를 묻는다. 질문이 바뀌면 답도 달라진다.

> **PR은 사람이 검토할 변경이 있을 때만 만든다.**

PR에는 작업한 Issue를 연결한다.

```text
Closes #23
```

여기까지는 별도의 사람 개입 없이 진행하는 것을 목표로 한다.

## 5. CI 실패와 복귀

PR이 생성되면 GitHub Actions가 독립된 환경에서 같은 `npm run verify`를 실행한다. CI의 역할과 실패 시 확인할 항목은 [03-verify.md](03-verify.md) 3절에 있다.

CI에서 실패하면 원인을 분석하고, 자동으로 수정할 수 있다면 구현 단계로 돌아간다.

```text
PR
   ↓
CI FAIL
   ↓
원인 분석 → 수정 → Local Verify PASS
   ↓
PR 업데이트
   ↓
CI에서 새 환경 생성 → CI / Review 재확인
   ↓
반복
```

### PR 이후 CI 수정 루프에도 상한을 둔다

CI 실패로 구현 단계에 복귀하는 횟수에도 상한을 둔다. 이 반복이 정해진 상한을 넘으면 더 이상 AI가 계속 수정하지 않고 `NEEDS_HUMAN`으로 넘긴다.

> **상한값은 Issue의 「구현 루프 최대 횟수」와 같다** (3절).
> 로컬 구현 루프와 합산하지 않고 이 구간에서 따로 센다.
> 이 구간의 시도도 같은 자리에 `loop=ci`로 남긴다 (3절).

CI 실패 자체를 별도의 핵심 반복 루프로 보지는 않는다. **핵심 구현 루프는 여전히 로컬의 구현 → verify → 수정 과정이고, PR 이후에는 별도의 제한된 수정 루프만 허용한다.**

## 6. AI Review

CI까지 통과하면 AI에게 코드 리뷰를 맡긴다. `verify`와 AI Review의 역할은 다르다.

```text
verify
→ 코드가 정해진 규칙과 테스트를 통과하는가?

AI Review
→ 구현 방법 자체에 문제가 없는가?
```

Review에서는 다음과 같은 것을 확인한다.

```text
불필요하게 복잡하게 구현하지 않았는가?
기존 구조를 이상하게 우회하지 않았는가?
Issue의 의도를 잘못 해석하지 않았는가?
위험한 변경이 포함되지 않았는가?
```

가능하면 구현을 담당한 AI와 리뷰를 담당한 컨텍스트를 분리한다.

```text
구현 AI
≠
Review AI 컨텍스트
```

Review AI는 코드를 직접 수정하지 않고 **리뷰 결과만 남긴다.** 리뷰에서 문제가 발견되더라도 그 결과를 자동으로 구현 AI에게 넘겨 수정시키지 않는다.

코드 리뷰는 종료 조건처럼 참·거짓으로 판정되는 영역이 아니다 ([02-contract.md](02-contract.md) 3절). Review AI가 구조·보안·유지보수성 문제를 제기하더라도, 그 지적이 실제로 수정해야 할 사항인지 그리고 **현재 Issue의 범위에서 받아들여야 하는지**는 7절에서 사람이 판단한다.

---

## 7. 마지막 사람 게이트

모든 자동 검증과 Review를 통과해도 자동으로 Merge하지 않는다.

```text
PR 내용
+
Local Verify PASS
+
CI Verify PASS
+
AI Review 결과
        ↓
[사람]
최종 확인
```

사람은 여기서 기계가 판단하기 어려운 부분을 확인한다.

```text
Issue의 실제 의도와 맞는가?
원했던 방식으로 구현됐는가?
AI Review의 지적 중 실제로 반영해야 할 것이 있는가?
화면이나 사용 흐름에 문제가 없는가?
구현 루프 기록이 상한 안에서 끝났는가?   (3절)
최종적으로 받아들일 수 있는 변경인가?
```

문제가 없다면 승인한다.

```text
승인
 ↓
Merge
 ↓
Issue Close
```

반대로 검증을 모두 통과했더라도 구현 방향이 Issue의 의도와 다르거나, Review 결과를 포함해 추가 수정이 필요하다고 판단되면 승인하지 않는다. 반려되면 5절과 같은 경로로 구현 단계에 복귀해 수정 → Local Verify → PR 업데이트 → CI → AI Review → 사람 재검토를 다시 거친다.

이때 PR을 새로 생성하지 않는다. 기존 PR이 해당 브랜치를 계속 추적하므로 수정 후 같은 브랜치에 Push한다.

### 반려 사유는 사람이 Issue comment에 남긴다

반려는 사람의 판단이므로 그 사유도 사람이 적는다. 자리는 시도 기록과 같은 해당 Issue의 comment이고, 형식은 3절의 헤더를 쓴다.

```text
HARNESS  run=1  loop=review
반려 사유: 총 재고에 폐기 거점이 섞여 안내 문구와 숫자가 어긋난다
```

**AI는 이 마커를 만들지 않는다.** AI가 반려를 선언할 수 있으면 사람의 게이트가 AI의 재시도 트리거가 된다.

이 comment가 AI가 다음에 무엇을 고칠지 읽는 유일한 입력이다. PR comment에만 적으면 세션이 끊겼을 때 복구 절차(3절)가 읽는 자리와 갈라진다.

### 반려 이후의 회차

반려 사유는 **새로운 수정 입력**이다. 그래서 이 마커가 다음 시도의 기준점이 되고, `loop=local`과 `loop=ci`는 여기서부터 다시 1회차로 센다 (3절).

```text
run       그대로 둔다. 계약은 바뀌지 않았다
attempt   반려 마커 이후부터 다시 센다. 상한값은 Issue에 적힌 그대로다
```

`run`을 올리지 않는 이유는 8절의 재진입과 다르기 때문이다. 그쪽은 사람이 **계약의 입력**을 보완해 실행 자체가 새로 시작되는 경우이고, 반려는 계약이 그대로인 채 **구현 방향**만 되돌리는 것이다.

반려 자체에는 상한을 두지 않는다. 계속할지 멈출지는 사람이 판단한다. 5절의 CI 수정 횟수에도 포함하지 않는다.

### 반려로 처리할 수 없는 것

반려 사유가 Issue의 요구사항이나 종료 조건 자체를 바꾸는 수준이면 반려가 아니다.

```text
같은 종료 조건을 다른 방식으로 만족시켜야 한다   → 반려. 같은 Issue로 복귀
종료 조건 · 기대 동작 · 문제 범위의 의미가 달라졌다 → 계약 변경. 8절의 경계를 따른다
```

경계는 8절 「정보가 부족했던 경우」와 같다 — **계약의 의미가 그대로인가**다. 의미가 달라졌다면 그 조건을 박제한 `tests/issues/issue-{번호}-{기능명}.test.ts`가 검증하는 내용도 달라진다. 그것은 comment로 지시할 일이 아니라 사람이 계약을 다시 쓸 일이다.

AI가 반려 사유를 읽고 **기존 종료 조건의 범위를 넘는 요구로 판단하면 구현하지 않는다.**

```text
반려 사유가 종료 조건 밖의 변경을 요구한다고 판단
      ↓
임의로 범위를 넓히지 않음
      ↓
그렇게 본 근거를 comment에 기록
      ↓
NEEDS_HUMAN
```

Issue 본문은 사람이 쓴 계약이고 comment는 실행 기록이다 ([00-ssot.md](00-ssot.md) 1절). 반려 사유를 계약 개정으로 읽기 시작하면 그 경계가 사라진다.

즉 **기계적 정답과 사람의 의도를 둘 다 통과해야 최종 완료**다.

## 8. 최종 상태와 그 이후

최종 작업 상태는 두 개로 둔다.

```text
MERGED
NEEDS_HUMAN
```

`SSOT_CONFLICT`, `BLOCKED`, `VERIFY_FAIL`, `CI_FAIL` 등은 작업 도중 발생하는 이벤트이지 최종 상태가 아니다. `PROTECTED_PATH_CHANGE`로 `BLOCKED`된 작업의 최종 상태는 `NEEDS_HUMAN`이다 (이벤트 표기는 [03-verify.md](03-verify.md) 6절).

전체 상태 전이는 다음과 같다. 각 구간의 절차는 해당 절이 원본이다.

```text
Issue
 ↓
SSOT 확인            ─ 충돌 → NEEDS_HUMAN              1절
 ↓
Implementation Loop  ─ 상한 도달 → NEEDS_HUMAN         3절
 ↓ SUCCESS
PR                                                    4절
 ↓
CI verify            ─ FAIL → 구현 단계 복귀
                       └ 상한 도달 → NEEDS_HUMAN       5절
 ↓ PASS
AI Review                                             6절
 ↓
사람 최종 판단        ─ 반려 → 구현 단계 복귀           7절
 ↓ 승인
MERGED
 ↓
Issue Close
```

즉 `NEEDS_HUMAN`으로 가는 경로는 두 군데다.

```text
1. 로컬 Implementation Loop에서 상한 도달
2. PR 이후 CI 수정 루프에서 상한 도달
```

사람의 판단이 즉시 필요한 문제가 발생한 경우에도 반복을 계속하지 않고 `NEEDS_HUMAN`으로 종료할 수 있다.

### NEEDS_HUMAN 이후 — 사람의 처분

`NEEDS_HUMAN`은 **AI의 루프가 멈춘 지점**이지, 작업이 끝났다는 뜻이 아니다. 그다음은 사람이 정한다.

```text
NEEDS_HUMAN
      ↓
[사람] Issue comment 확인
 ├─ 전제는 맞고 정보만 부족했다 → 정보 보완 → 같은 Issue로 구현 루프 재진입
 ├─ 전제 자체가 틀렸다         → 코드 변경 · PR 없이 Issue Close
 └─ 보류                       → NEEDS_HUMAN 유지
```

갈림길은 **Issue의 전제가 성립하는가**다. 전제가 맞는데 판단할 근거만 부족했다면 계약은 살아 있다. 전제가 틀렸다면 계약 자체가 성립하지 않는다.

### 정보가 부족했던 경우 — 같은 Issue로 재진입

사람이 부족했던 것을 채우면 **같은 Issue를 다시 구현 루프에 넣을 수 있다.**

```text
종료 조건을 판정할 수 없었다  → 사람이 기준일 · 입력 · 기대값을 채운다    02-contract.md 2.1 ①
재현 조건이 부족했다          → 사람이 재현 절차를 채운다
읽기 범위가 부족했다          → 사람이 범위를 열거나 목록을 갱신한다      00-ssot.md 3절
기준이 충돌했다               → 사람이 SSOT를 갱신한다                    00-ssot.md 4절 · 6절
```

```text
[사람] 정보 보완 · 기준 갱신
      ↓
같은 Issue · 같은 브랜치로 구현 루프 재진입  (3절)
```

**새 Issue를 열지 않는다.** 계약의 대상은 그대로이고, 그 계약을 판정할 근거가 이제 갖춰진 것이다.

경계는 **계약의 의미가 그대로인가**다.

```text
의미는 그대로. 판정에 필요한 정보만 채웠다          → 보완. 같은 Issue로 재진입
기대 동작 · 문제 범위 · 종료 조건의 의미가 달라졌다   → 계약 변경. 새 Issue
```

종료 조건이 바뀌면 그 조건을 박제한 `tests/issues/issue-{번호}-{기능명}.test.ts`가 검증하는 내용도 바뀐다. 번호와 이름은 그대로인 채로 — 아래 「나중에 실제 문제를 발견하면 새 Issue를 연다」가 막는 것과 같은 일이다.

보완이라면 재진입한 루프는 **2절의 종료 조건 처리부터 다시 수행한다.** 채워진 정보로 판정 가능성을 다시 본다.

#### 재진입한 루프의 횟수

```text
사람이 입력을 실질적으로 보완했다   → 새 실행. 1회부터 다시 센다
                                     (재현 조건 · 종료 조건의 판정 정보 · 기준 · 읽기 범위)

조건 변경 없이 다시 시도한다        → 같은 실행. 기존 횟수를 이어서 센다
```

입력이 달라졌으면 AI가 푸는 문제가 달라진 것이므로, 이전 시도의 실패를 새 시도의 몫으로 세지 않는다. 반대로 **같은 입력으로 다시 돌리는 것은 3절이 상한을 둔 바로 그 반복이다.** 거기서 횟수를 초기화하면 상한이 사라진다.

무엇이 「실질적 보완」인지는 사람이 판단한다. 재진입시킬 때 그 판단을 comment에 남긴다.

```text
HARNESS  reentry  run=2
보완한 것: 종료 조건 3건을 기준일·기대값을 넣어 다시 씀
```

이 마커가 **새 실행의 시작점**이다. 다음 세션은 여기서부터 1회차로 센다 (3절).

**AI는 이 마커를 만들지 않는다.** AI가 `run`을 올릴 수 있으면 상한을 스스로 풀 수 있다.

마커가 없거나 형식이 깨져 읽을 수 없으면 **초기화만 인정하지 않고, 회차는 이전 실행에서 이어서 센다.** 모호하면 상한이 유지되는 쪽으로 기운다.

시도 기록 자체가 깨져 회차를 확정할 수 없는 경우는 다르다 — 그때는 세지 않고 `NEEDS_HUMAN`이다 (3절).

### 전제가 틀렸던 경우 — PR 없이 Close

Issue의 전제가 성립하지 않는다고 사람이 판단하면, **코드를 바꾸지 않고 PR도 만들지 않은 채 Issue를 닫는다.**

```text
NEEDS_HUMAN
      ↓
[사람] 수정 불필요 판단
      ↓
코드 변경 없음 · PR 없음
      ↓
Issue Close (판단 근거를 comment에 남긴다)
```

이때 남는 산출물은 Issue의 comment 기록뿐이다. 바꾼 코드가 없으므로 회귀 테스트로 남길 종료 조건도 없다 — 지키게 할 동작이 새로 생기지 않았기 때문이다.

이번 실행에서 만든 종료 조건 테스트가 있다면 **함께 지운다.**

```text
지운다        tests/issues/issue-{현재 번호}-*.test.ts 중
              이번 실행에서 새로 만들었고 아직 Merge되지 않은 것

지우지 않는다  Merge되어 회귀 테스트로 남은 것
              과거 Issue의 것은 애초에 쓰기 금지다 ([00-ssot.md](00-ssot.md) 5절)
```

전제가 틀렸다면 그 전제로 쓴 테스트도 틀렸다. 남겨두면 **잘못된 동작을 정답으로 고정하고**, 다음 작업은 그것을 지켜야 할 계약으로 읽는다.

이 삭제는 Close 처분의 일부이므로 사람이 판단한다. **AI가 `verify`를 통과시키려고 테스트를 지우는 것과는 다르다** ([00-ssot.md](00-ssot.md) 5절) — 그쪽은 계약이 살아 있는데 심판을 치우는 것이고, 이쪽은 계약 자체가 성립하지 않았다고 사람이 판정한 경우다.

닫는 이유는 사람이 남긴다. 나중에 같은 증상이 다시 보고됐을 때 **「그때 왜 고치지 않기로 했는가」**를 찾을 수 있어야 한다.

### 나중에 실제 문제를 발견하면 새 Issue를 연다

닫힌 Issue를 되살려 다른 문제를 담지 않는다. 조사 과정에서 발견한 별개의 문제도 마찬가지다.

```text
Close된 Issue
      ↓
나중에 실제 문제 발견
      ↓
기존 Issue 재사용하지 않음
      ↓
새 Issue 발행
```

Issue 번호는 브랜치명 · 테스트 파일명 · 보호 경로 판정의 입력이고(1절), 종료 조건 테스트는 Merge 후 회귀 테스트로 남는다([02-contract.md](02-contract.md) 5절). **한 번호가 두 계약을 가리키면 「이 검증이 어느 계약에서 나왔는가」를 이름으로 되짚을 수 없다.**

발견된 문제는 전제도 종료 조건도 닫힌 Issue의 것이 아니다. 별도 계약으로 연다.

### 상태를 새로 만들지 않는 이유

코드 변경 없이 닫힌 작업의 마지막 상태는 `NEEDS_HUMAN`이고, Issue Close는 그 상태에 대한 사람의 처분이다. 이를 위해 상태를 새로 만들지 않는다.

```text
상태  = AI가 어디서 멈췄는가
처분  = 사람이 그것을 어떻게 할 것인가
```

둘을 한 축에 섞으면 `NEEDS_HUMAN`이 「사람이 아직 보지 않았다」와 「사람이 보고 끝냈다」를 동시에 뜻하게 된다. 그 구분은 Issue의 open/closed가 이미 갖고 있다.

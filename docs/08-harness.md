## 0. 한 줄 요약

**사람이 문제와 종료 조건을 정의하면, AI는 검증을 통과할 때까지 반복해서 수정한다. 단, 정해진 횟수 안에 해결하지 못하면 실패를 인정하고 사람에게 넘긴다.**

완료 여부는 AI의 설명이 아니라 **실행 가능한 검증 결과**가 판단한다.

검증은 별도의 두 명령으로 분리하지 않는다.

```text
공통 규칙 검증
+
Issue별 종료 조건을 기계화한 테스트
        ↓
npm run verify 하나에 누적
```

Issue별 테스트는 해당 Issue가 끝난 뒤에도 삭제하지 않고 회귀 테스트로 남긴다.

CI는 별도의 심판이 아니라, **로컬에서 통과한 `npm run verify` 전체가 독립된 환경에서도 동일하게 통과하는지 확인하는 재현성 게이트**다.

---

## 1. 이 하네스가 하는 일

이 하네스의 목적은 재고관리 프로그램 자체를 완성하는 것이 아니다.

M1~M7까지 만든 재고관리 PoC에 올라오는 실제 유지보수 이슈를,

> **AI가 사람 대신 읽고, 구현하고, 검증하고, PR까지 처리한다.**

그렇게 운영할 수 있는 구조를 만드는 것이 목적이다.

전체 흐름은 다음과 같다.

```text
[사람]
Issue 작성 + 종료 조건 정의
        ↓
[AI]
Issue 분석 → 구현 → npm run verify
   ├─ 실패 → 원인 분석 → 수정 → 재검증
   └─ 성공 → PR 생성
        ↓
[GitHub Actions]
독립된 테스트 환경 준비 → npm run verify → AI Review
        ↓
[사람]
PR 내용 + CI 결과 + Review 결과 확인
        ↓
├─ 승인 → Merge → Issue Close
└─ 반려 → 사유를 Issue comment에 기록 → 구현 단계로 복귀
```

각 단계의 규칙은 [`04-loop.md`](harness/04-loop.md)가 원본이다.

여기서 중요한 것은 단순히 AI를 반복시키는 것이 아니다. 두 가지를 먼저 정해야 한다.

1. **무엇을 완료라고 판단할 것인가**
2. **AI가 해결하지 못했을 때 언제 멈출 것인가**

즉 성공뿐 아니라 **실패했을 때의 종료 방법까지 하네스에 포함한다.**

---

## 2. 사람과 AI의 경계

사람의 개입 지점은 크게 시작과 끝이다.

```text
[사람]  Issue + 종료 조건
          ↓
[AI]    구현 · 검증 · 재시도 · PR 생성 · CI 결과 확인 · AI Review 수행
          ↓
[사람]  최종 승인
```

**시작** — 사람이 유지보수 Issue와 종료 조건을 정의한다.
**끝** — 기계 검증을 통과한 PR과 AI Review 결과를 사람이 최종 확인한다.

그 사이 과정은 가능한 한 AI가 담당한다. 사람의 별도 지시 없이 로컬 검증에 성공하면 PR 단계로 넘어간다.

## 3. 핵심 원칙

각 원칙이 실제로 어떤 규칙과 값으로 구현되는지는 오른쪽 문서가 원본이다. 여기에 값이나 절차를 다시 적지 않는다.

| # | 원칙 | 원본 |
| --- | --- | --- |
| 1 | **구현보다 기준을 먼저 정한다.** AI가 무엇을 따라야 하는지 모르는 상태에서 작업을 시작하지 않는다 | [`01-build.md`](harness/01-build.md) |
| 2 | **SSOT의 역할을 나눈다.** 제품 요구사항, 아키텍처, 하네스 정책, 개별 Issue가 각각 무엇의 원본인지 명확하게 한다 | [`00-ssot.md`](harness/00-ssot.md) 1절 |
| 3 | **기준이 충돌하면 AI가 결정하지 않는다.** 구현을 멈추고 `NEEDS_HUMAN`으로 넘긴다 | [`00-ssot.md`](harness/00-ssot.md) 4절 |
| 4 | **반복보다 판정을 먼저 만든다.** 언제 끝나는지 모르는 반복부터 만들지 않는다 | [`01-build.md`](harness/01-build.md) 1절 |
| 5 | **종료 조건은 가능한 한 실행 가능하게 만든다.** 판정에 필요한 입력·기준·기대 결과가 빠진 조건은 AI가 임의로 해석하거나 보완하지 않는다 | [`02-contract.md`](harness/02-contract.md) 2절 |
| 6 | **AI의 말을 완료 근거로 사용하지 않는다.** 실행 결과가 판단한다 | [`03-verify.md`](harness/03-verify.md) 1절 |
| 7 | **기존 기능도 함께 검증한다.** 새로운 문제를 해결하면서 기존 기능을 깨뜨리지 못하게 한다 | [`03-verify.md`](harness/03-verify.md) 2절 |
| 8 | **AI는 심판을 수정할 수 없다.** 통과하지 못했다고 검증 기준을 느슨하게 만들 수 없다 | [`00-ssot.md`](harness/00-ssot.md) 5절 · `scripts/verify/protected.ts` |
| 9 | **반복에는 상한이 있다.** 해결하지 못하는 문제를 무한히 붙잡지 않는다 | [`04-loop.md`](harness/04-loop.md) 3절 |
| 10 | **실패해도 제대로 멈춰야 한다.** 해결하지 못하면 `NEEDS_HUMAN`으로 넘긴다 | [`04-loop.md`](harness/04-loop.md) 8절 |
| 11 | **테스트 DB는 매 검증마다 새로 만든다.** 로컬과 CI가 각각 독립된 DB를 만든다 | [`03-verify.md`](harness/03-verify.md) 5절 |
| 12 | **PR 이후 수정도 무한히 반복하지 않는다** | [`04-loop.md`](harness/04-loop.md) 5절 |
| 13 | **CI는 두 번째 심판이 아니다.** 같은 명령을 깨끗한 환경에서 다시 실행해 전체 판정이 재현되는지 확인한다 | [`03-verify.md`](harness/03-verify.md) 3절 |
| 14 | **마지막 판단은 사람이 한다.** 기계 검증을 모두 통과했더라도 사람이 최종 승인한다 | [`04-loop.md`](harness/04-loop.md) 7절 |

## 최종 요약

```text
먼저 SSOT 정책을 정한다.
        ↓
사람이 Issue와 종료 조건을 만든다.
        ↓
AI가 Issue와 관련 SSOT를 확인한다.
        ↓
충돌하면 구현하지 않고 NEEDS_HUMAN으로 넘긴다.
        ↓
문제가 없으면 AI가 구현한다.
        ↓
기존 테스트 DB를 제거하고 새 테스트 DB를 준비한다.
        ↓
npm run verify가 판정한다.
        ↓
실패하면 다시 수정한다.
        ↓
정해진 횟수 안에 해결하지 못하면 사람에게 넘긴다.
        ↓
성공하면 PR을 만든다.
        ↓
GitHub Actions가 새로운 테스트 DB를 만든다.
        ↓
같은 npm run verify를 다시 실행한다.
        ↓
AI가 코드를 Review한다.
        ↓
사람이 PR 내용과 Review 결과를 보고
실제 의도와 맞는지 마지막으로 확인한다.
        ↓
반려하면 사유를 Issue comment에 남기고
그 사유를 입력으로 구현 단계로 돌아간다.
        ↓
같은 PR을 그대로 쓰고, 다시 여기까지 온다.
        ↓
승인하면 Merge하고 Issue를 종료한다.
```
